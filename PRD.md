## 1. Product Summary

SIGNAL is a web application that converts a user's existing digital consumption (YouTube likes, TikTok/Instagram history, exported watch data) into a **validated business opportunity** and a **tiered execution blueprint** ("roadmap") for turning it into income.

The core insight: most people are already consuming content that implies a latent, marketable skill (e.g., 40 hours of Blender tutorials + Unreal lighting ≠ "watches art videos" → latent skill `3d_environment_art`). SIGNAL surfaces that skill, matches it against curated business models, filters by the user's hard constraints (capital, hours, risk, camera aversion), and delivers a concrete, free 14-day plan — then monetizes the momentum it creates.

The product loop is deliberately engineered to **deliver a tangible artifact before asking for payment**, then paywall exactly the parts that create momentum (automation, lead-gen, exclusivity, trend intelligence).

**Positioning / aesthetic directive:** Dark minimalist, brutalist, industrial. Pure `#000000` backgrounds, white 1px structural borders, zero rounded corners, monospace type (JetBrains Mono / IBM Plex Mono), one functional accent color for the Saturation Meter and CTAs. The UI reads as a military-grade terminal / control panel. Motion is mechanical (cursor blinks, count-ups, hard state transitions) — no bouncy easing. This is a hard visual requirement, not a preference (see §5.13).

## 2. Goals, Non-Goals, and Success Metrics

### 2.1 Goals

1. **G1 — Activation:** Get a first-time visitor from landing page to a rendered (blurred) blueprint in **≤ 20 minutes**, with zero payment required.
2. **G2 — The "how did it know?" moment:** ≥ 60% of users who reach the results screen report/behave as if the skill-to-opportunity match felt uncannily accurate (measured via post-render survey + conversion uplift).
3. **G3 — Monetize momentum, not access:** Revenue is generated by upsells *after* value is demonstrated (deploy, unlock, license, alerts, fulfillment), never by blocking the initial artifact.
4. **G4 — Defensible scarcity:** Every scarcity number shown to users is real (computed from actual data), never fabricated. See §9.
5. **G5 — Scale-safe async architecture:** The UI never calls the LLM synchronously. All heavy work is queued; a viral spike must degrade gracefully (§7.3, NFR-07).

### 2.2 Non-Goals (for MVP)

- Mobile native apps (responsive web only).
- TikTok OAuth ingestion (no consumer watch-history API exists — upload-only, permanent).
- Marketplace marketplace-fulfillment (Phase 3).
- Multi-language UI beyond English (en-CA / en-US; fr-CA is a post-launch candidate — see Open Questions).
- Social features, feeds, community.
- Desktop app.

### 2.3 Success Metrics (North Star + guardrail metrics)

| Metric | Definition | Target |
|---|---|---|
| **Activation rate** | Quiz starts → blueprint rendered (blurred) | ≥ 35% |
| **Quiz completion rate** | Quiz sessions completed / started | ≥ 60% |
| **Ingestion success rate** | Consumption events parsed + clustered / uploads started | ≥ 90% (per upload) |
| **Unlock rate** | Basic → Premium (paywall) conversion within 30 days | ≥ 8% of activated users |
| **Deploy attach rate** | $79 deploy purchases / premium unlocks | ≥ 25% |
| **Buy-out attach rate** | $199 license purchases / premium users seeing local density > 0 | ≥ 5% |
| **Trend-alert subscriber rate** | Subscribers / premium users, 90 days | ≥ 10% |
| **CAC payback** | Blended CAC vs. LTV | ≤ 6 months |
| **Guardrail: churn after unlock** | Premium churn within 90 days | ≤ 12% |
| **Guardrail: support load** | Tickets per 1,000 activated users | ≤ 15 |
| **Guardrail: complaint rate** | Complaint/opt-out rate re: urgency mechanics | ≤ 0.5% of activated users |
| **Guardrail: processing freshness** | p95 job → event → UI latency | ≤ 3 s per stage |

## 4. The Core Product Loop (End-to-End Journey)

The single journey everything is built around. States are explicit; every screen has a job.

```
Landing page
  → [FR-LP] Constraint Quiz (9 steps, no auth, session-token state)
  → [FR-AU] Soft account creation (magic link, no password)
  → [FR-IG] Data ingestion choice (OAuth or upload)
  → [FR-AS] Async processing screen (streamed status events, SSE)
  → [FR-VM] Vector mapping completes ("how did it know?" moment)
  → [FR-BP] Basic Blueprint renders behind partial blur
  → [FR-TR] Single "Unlock full roadmap" CTA (paywall)
  → [FR-MP] Monetization surfaces (deploy, license, alerts, marketplace)
```

**Design principle (non-negotiable):** the first artifact (the basic blueprint) is delivered *before* any payment ask. Payment asks appear only after the user has seen their name, their skill, their local market reflected back.

**Abandonment handling:** the quiz is persisted to `quiz_sessions` keyed by an anonymous session UUID *before* account creation, so every abandoned quiz is remarketable (via email capture at the magic-link step, or retargeting pixel keyed to the session UUID) without requiring an account.

## 5. Functional Requirements

### 5.1 Landing Page (`FR-LP`)

| ID | Requirement |
|---|---|
| FR-LP-01 | Single CTA-led landing page. One primary CTA: **"Start the constraint quiz"** (or equivalent). No signup wall. |
| FR-LP-02 | Page must communicate the loop in ≤ 5 seconds: *consumption → skill → validated opportunity → roadmap*. |
| FR-LP-03 | The Saturation Meter (§5.9) is visible on the landing page as a live instrument readout (real aggregate data only — see ETH-02). |
| FR-LP-04 | Edge middleware resolves coarse location to seed a placeholder Local Density readout instantly (e.g., "2 operators near you running blueprints right now"), replaced with exact data post-login (FR-SAT-06). |
| FR-LP-05 | `lighthouse` performance budget: LCP ≤ 2.5 s, CLS ≤ 0.1 on 4G (NFR-02). |
| FR-LP-06 | Landing page sets the anonymous `session_id` cookie (`quiz_session`) if absent, and links all downstream quiz/ingestion state to it. |

### 5.2 Constraint Quiz (`FR-QZ`)

A 9-step typed flow. **No authentication** during the quiz. All state persists server-side to `quiz_sessions` (see §6) keyed by the anonymous session UUID.

**Step order (fixed):**

| Step | Field(s) | UI | Notes |
|---|---|---|---|
| 1 | `liquid_capital_cents` | Discrete buckets: `0`, `$50k`, `$200k`, `$1M+` (stored in cents) | Bucket, not slider — precision isn't needed; commitment is. |
| 2 | `weekly_hours` | Slider 0–60 (smallint) | |
| 3 | `risk_tolerance` | Enum `safe | balanced | degenerate` | Label copy TBD — see Open Questions. |
| 4 | `time_horizon_days` | Smallint (expectation of first $) | |
| 5–7 | Trait tradeoffs | Forced-choice pairs (e.g., *"build in public vs. build in silence"*) | 3 questions → Big-Five-lite vector (see FR-QZ-04). |
| 8 | `hard_constraints` | Multi-select: `no_camera`, `no_cold_calls`, `no_weekend_work`, etc. | **Most important field downstream** — hard filter, never a soft weight (FR-BP-05). |
| 9 | `existing_skills`, `geo_point` | Free-text skills + postal code | Skills reconciled against the vector layer later. |

| ID | Requirement |
|---|---|
| FR-QZ-01 | Every step auto-saves to `quiz_sessions` (PATCH per step). A user who abandons and returns (same cookie) resumes at the exact step. |
| FR-QZ-02 | No account or email is required to start or complete the quiz. Email is requested only at the magic-link step (FR-AU). |
| FR-QZ-03 | Quiz session is `completed` when step 9 is persisted; this fires the abandonment-remarketing hook (email/SMS/ads) if the user doesn't proceed to account creation within 24 h. |
| FR-QZ-04 | Trait questions are **never** asked directly ("are you an introvert?"). Each forced-choice answer maps to a delta on a compressed Big-Five-lite vector (3 dims used: introversion, conscientiousness, openness), stored as `numeric(3,2)` 0.00–1.00. The inference mapping table lives in code, is versioned, and is unit-tested. |
| FR-QZ-05 | `geo_point` is derived from postal code (US ZIP5 / Canadian postal code, geocoded server-side) and stored as PostGIS `geography(Point,4326)`. |
| FR-QZ-06 | Rate-limit quiz writes (e.g., 30 req/min per session) to prevent abuse of the session UUID (NFR-05). |
| FR-QZ-07 | Session UUIDs are high-entropy (≥ 128-bit, `crypto.randomUUID`), never enumerable. |

### 5.4 Data Ingestion Layer (`FR-IG`)

Two paths, unified into normalized `consumption_events`.

#### Path A — OAuth pipeline (official APIs)

| Provider | Data via OAuth | Notes |
|---|---|---|
| YouTube | Data API v3: liked videos, watch later, subscriptions | Required scopes: `youtube.readonly`. Pagination via `nextPageToken`. |
| Instagram | Graph API: saved/engaged media (business/creator accounts only) | Personal-account saved posts are **not** available; if OAuth scope unavailable for the account type, gracefully fall back to "upload only" for that user (FR-IG-05). |
| TikTok | **Not available** — upload-only, permanent | No consumer watch-history API exists. UI must set this expectation explicitly to avoid user frustration. |

| ID | Requirement |
|---|---|
| FR-IG-01 | OAuth tokens encrypted at rest (libsodium XChaCha20-Poly1305; keys in KMS) in `oauth_connections`. **Never** log tokens or raw token payloads. |
| FR-IG-02 | Refresh handled by a scheduled worker (`token_refresh` queue, §7.3). Expired-and-unrefreshable connections are marked `revoked` and the user is prompted to re-link. |
| FR-IG-03 | Each provider implements a typed adapter: `fetch_events(cursor) -> NormalizedEvents[]` mapping provider fields → canonical `consumption_events` schema. Adapters are contract-tested against recorded fixtures (NFR-08). |
| FR-IG-04 | Ingestion is incremental + idempotent: dedupe key = `(source, provider_event_id)`; re-runs insert nothing. |
| FR-IG-05 | If a provider returns 0 events or an auth failure, the user sees a typed error state with a "try export upload instead" escape hatch. Never show a blank "generating" screen. |

#### Path B — Fallback worker-queue (data exports)

| Upload type | Expected format |
|---|---|
| Google Takeout | `watch-history.json` (JSON array of watch events) |
| TikTok data download | `Video Browsing History` JSON |
| Instagram export | `content/posts_1.json` etc. (JSON) |

| ID | Requirement |
|---|---|
| FR-IG-06 | Upload lands in object storage (S3/R2) via presigned PUT (client-side, no server bandwidth), then enqueues `parse_export` job (BullMQ). |
| FR-IG-07 | Worker fingerprints format by filename + JSON shape (schema sniffing), then **stream-parses** (never load >200 MB into memory; use a streaming JSON parser, e.g., `stream-json` / line-based parsing). Hard per-file memory cap with failure if exceeded. |
| FR-IG-08 | Parsing is **checkpointed and idempotent**: worker writes cursor + dedupe hashes after each N records; a crashed worker resumes from the last checkpoint instead of re-reading the file. |
| FR-IG-09 | Uploads are virus-scanned (AV hook) and size-limited (e.g., ≤ 500 MB compressed; configurable). |
| FR-IG-10 | Progress is streamed to the client: `records_parsed`, `estimated_total`, `stage` (upload → sniff → parse → normalize → emit). |
| FR-IG-11 | User can select a subset (e.g., "only YouTube, last 12 months") before processing; selection persists on the job payload. |

### 5.5 Async Processing & Streamed Status (`FR-AS`)

| ID | Requirement |
|---|---|
| FR-AS-01 | **The UI never calls the LLM synchronously.** API routes enqueue jobs and return `202 Accepted + job_id` (FR-AS-05). |
| FR-AS-02 | Client subscribes to a job event stream (SSE preferred; WebSocket fallback) at `GET /api/jobs/:jobId/events`. |
| FR-AS-03 | The processing screen is a live telemetry readout (aesthetic directive): stage name, progress bar (monospace, mechanical), event log lines. It must look like a machine working, not a spinner. |
| FR-AS-04 | Event stream survives disconnects: client replays from `Last-Event-ID`; server keeps a short event ring buffer (Redis, TTL 15 min). |
| FR-AS-05 | Job lifecycle: `queued → running → succeeded | failed | dead_lettered`. Failures retry with exponential backoff (per-queue config §7.3); after N retries, job → DLQ + user-visible typed error with "contact support / retry" actions. |
| FR-AS-06 | Every stage publishes a structured event (see §7.4 schema) so the frontend can render stage-accurate UI and so metrics can be derived per stage. |

### 5.6 Vector Mapping System (`FR-VM`)

The LLM orchestrator runs **three stages** over the consumption corpus:

**Stage 1 — Cluster.** Embed every `title + tags + channel` string with a small embedding model (e.g., `text-embedding-3-small`, 1536-dim) into a `pgvector` column. Approximate clustering (HNSW index + cosine) collapses thousands of events into **15–40 thematic clusters**. Clustering runs on the `generate_blueprint` job path (per-user) and nightly in aggregate for the opportunity layer.

**Stage 2 — Skill extraction.** For each cluster, the orchestrator prompts an LLM to label the **latent capability implied by sustained consumption** — not the topic. *"40 hours of Blender tutorials + Unreal lighting" → latent skill `3d_environment_art`*, not "watches art videos." Each inferred skill gets:
- `confidence` (0.00–1.00)
- `recency_weight` (exponential decay by event recency)

**Stage 3 — Skill-to-opportunity match.** Inferred skills are embedded and matched (cosine) against the curated `opportunity_vectors` table (business models with required-skill embeddings + constraint metadata), then **intersected with the user's hard constraint filters** (capital floor, hours, camera, risk, horizon).

| ID | Requirement |
|---|---|
| FR-VM-01 | Embedding model, dimension (1536), and prompt templates are pinned by version; a model bump invalidates vectors (backfill job) — never silently mix vector spaces. |
| FR-VM-02 | HNSW index (`vector_cosine_ops`) on embedding columns; index build is a migration task with a maintenance window. |
| FR-VM-03 | Clustering is deterministic per (user, corpus snapshot): store cluster assignments in `consumption_clusters` so re-renders and A/B tests don't reshuffle. |
| FR-VM-04 | Skill extraction prompt includes the user's constraint profile as *context* (never as a filter at this stage) and a strict output schema (JSON, validated, retried on parse failure). |
| FR-VM-05 | Match results are a **ranked shortlist of ≥ 3 and ≤ 5 validated opportunities** with per-opportunity match rationale (which skills, which evidence clusters) — the rationale is user-visible ("how did it know?"). |
| FR-VM-06 | Zero matches (cold start / tiny corpus): show a "not enough signal" state with a re-ingest CTA, plus 1 generic starter blueprint. Never show an empty screen (FR-AS-04 spirit). |
| FR-VM-07 | Opportunity curation is human-reviewed (operations role) before an `opportunity` is published to `opportunity_vectors`; new opportunities require ≥ 3 evidence references and a filled constraint metadata row. |
| FR-VM-08 | Per-user processing budget: LLM cost per blueprint is monitored and capped (spend alert at 2× expected p50; hard per-user monthly cap) — see NFR-10. |

### 5.7 Blueprint Generator (`FR-BP`)

The roadmap is **one object with tier-gated nodes**. The generator always produces the full tree; the renderer (and the API serializer) masks premium nodes for basic-tier users.

```
blueprint {
  id, user_id, opportunity_id,
  tier: enum('basic','premium'),
  nodes: jsonb,   // tree: phases -> tasks; each node has {tier_gate: 'basic'|'premium'}
  density_snapshot: numeric(4,1),
  created_at
}
```

#### Phase 1 — Basic Tier (Zero-to-One), free

| ID | Requirement |
|---|---|
| FR-BP-01 | **14-day zero-cost skill acquisition roadmap**: daily nodes, each with (a) a specific free resource (named video/playlist/doc with URL), (b) a concrete deliverable, (c) a self-check. Sequenced so that by day 14 the user has **one portfolio artifact**. |
| FR-BP-02 | **$0 free-tier tech stack**, pinned to their opportunity model: exact tools with names, links, and free-tier limits (e.g., Cal.com free, Notion free, Canva free, free domain alias). No "consider using a CRM" — always concrete: tool, plan, limit. |
| FR-BP-03 | **Hyper-personalized cold outreach scripts** in 3 variants (DM, email, in-person), generated against inferred skill + local market, pre-filled with the user's actual niche and geo. |
| FR-BP-04 | Basic tier is always free, always available, and must be genuinely completable — this is the product's trust engine. |
| FR-BP-05 | `hard_constraints` is a **hard filter** at generation time (opportunity excluded if any constraint conflicts), never a soft weight. Enforcement is server-side. |
| FR-BP-06 | Blueprint generation must honor `density_snapshot` and `local_license` checks at generation time (FR-SAT-11, FR-MP-06). |
| FR-BP-07 | Nodes are immutable once generated (versioned on regeneration); day-1 check-ins are possible ("mark done") and sync to a progress view. |

### 5.9 Saturation Engine (`FR-SAT`)

#### Global Density Score (0.0% – 100.0%)

Computed per `opportunity_id`, recomputed nightly + on-demand:

```
GlobalDensity = clamp(
    w1 * search_trajectory_factor
  + w2 * active_blueprint_ratio
  + w3 * marketplace_supply_factor
  , 0, 100)
```

| Term | Definition | Source |
|---|---|---|
| `search_trajectory_factor` | **Slope** of search volume, not raw volume (d/dt, normalized) | External search-trend data, sampled daily into `search_trajectories` |
| `active_blueprint_ratio` | Users running this model / TAM proxy (TAM = matched-qualified users, §5.6) | Internal |
| `marketplace_supply_factor` | Gig-worker supply for this model (Phase 3 data; seeded with curated estimates pre-launch) | Internal / curated |
| `w1..w3` | Tunable per category (`category_weight_config`) | Config table |

| ID | Requirement |
|---|---|
| FR-SAT-01 | Score displayed to **one decimal place** (instrument-readout feel). The rising-slope behavior is intentional: a rising slope raises density faster ("everyone's about to pile in"). |
| FR-SAT-02 | Nightly recompute job (`density_recompute`) writes `density_snapshots`; on-demand recompute is triggered by admin and by opportunity publication. |
| FR-SAT-03 | Weight config is versioned (JSON in DB) and hot-reloadable; all recomputations log the weight-version used. |
| FR-SAT-04 | A `how is this computed?` disclosure link is required on every density surface (ETH-02). |

#### Local Density Index & Geo-Fencing

```
LocalDensity(user) = COUNT(active users running opportunity_id)
  WHERE ST_DWithin(user.geo_point, blueprint.geo_point, 40233.6)  -- 25 miles in meters
```

| ID | Requirement |
|---|---|
| FR-SAT-05 | PostGIS `ST_DWithin` query against `blueprints.geo_point` (GIST index required, NFR-01). |
| FR-SAT-06 | UI surfaces a live count: *"N other operators within 25 mi are running this exact blueprint."* **The number is real** (active premium + basic users) — defensible scarcity (ETH-01). |
| FR-SAT-07 | Local density is cached (Redis, TTL 5 min) and seeded at the edge (FR-LP-04); stale reads degrade to "recently updated" rather than fabricated numbers. |
| FR-SAT-08 | The local density count is the direct on-ramp to the Buy-Out License (FR-MP-05): when count ≥ 1, the buy-out CTA appears on the blueprint. |
| FR-SAT-09 | Privacy: counts are aggregate (≥ 1 shown as exact small numbers only with user consent to be counted; users can opt out of being counted in §9). Never expose individual user identities or exact coordinates. |

|---|---|

### 5.11 Freelance Fulfillment Marketplace — 20% take (Phase 3, spec now)

| ID | Requirement |
|---|---|
| FR-MK-01 | Users who don't want to build assets are routed to vetted gig-workers. Platform escrows payment, takes **20%**. |

### 7.3 Worker / queue matrix (BullMQ on Redis; Celery equivalent in Python services)

| Queue | Workload | Concurrency | Rate limit | Retry / backoff | Notes |
|---|---|---|---|---|---|
| `parse_export` | IO-heavy stream parsing | High (per-CPU) | Per-bucket storage quota | 3 × exp backoff → DLQ | Checkpointed (FR-IG-08) |
| `generate_blueprint` | LLM-heavy orchestrator | Low, capped | **Respects provider TPM/TPM budget** | 2 × exp → DLQ | Cost-capped (NFR-10) |
| `token_refresh` | OAuth refresh | Med | Per provider | 3 × exp → mark `revoked` | Scheduled |

### 7.4 Streaming protocol (SSE)

`GET /api/jobs/:jobId/events` — `text/event-stream`.

```
event: status
data: {"jobId":"...","stage":"embed","percent":42,"message":"Embedding 1,284 events…",
       "payload":{"clusterCount":23},"ts":"2026-08-28T12:00:00Z"}
id: 128
```

Stages: `queued → ingest → embed → cluster → extract → match → compose → ready | failed`. Client renders stage names verbatim (mechanical readout aesthetic). Server keeps a Redis ring buffer (TTL 15 min) keyed by jobId for replay via `Last-Event-ID` (FR-AS-04). Terminal events: `blueprint.ready` (includes blueprint id), `blueprint.error` (typed, retryable flag).

### 7.5 Embedding & clustering pipeline detail

1. `generate_blueprint` worker loads the user's `consumption_events` (all sources).
2. Batch-embeds `title + tags + channel` (batching per provider TPM budget; checkpointed).
3. Writes embeddings to `consumption_events.embedding` (upsert).
4. Approximate clustering (HNSW + cosine; e.g., HDBSCAN-style or k-means with silhouette scoring) → 15–40 clusters → persisted to `consumption_clusters`.
5. LLM stage per cluster: label latent skill (schema-constrained output) → `user_skill_vectors` with confidence + recency decay.
6. Cosine-match skill embeddings against `opportunity_vectors` → candidates.
7. Hard-filter candidates on `constraint_profile` (capital, hours, camera, cold calls, horizon) + `local_license` check.
8. LLM compose stage writes the full blueprint tree (basic + premium nodes) in one schema-validated JSON document; then renderer/serializer masks per entitlement.

## 9. Ethics, Compliance & Guardrails

The saturation engine manufactures urgency **by design**, and the buy-out license lets customers *remove* options from neighbors. These mechanics are powerful; this section defines the guardrails that keep them defensible, legal, and audit-safe. **These are product requirements, not suggestions.**

| ID | Requirement |
|---|---|
| ETH-01 | **Honest telemetry only.** Every density number, local count, and alert shown to a user must be derived from real data (internal counts, real search-slope samples, real worker supply). Fabricating or inflating scarcity numbers is a production-blocking defect. |
| ETH-02 | **Disclosure.** Every density surface carries a "how is this computed" disclosure (FR-SAT-04) that describes the components in plain language. The buy-out purchase flow explains plainly that the license removes the opportunity from other users' future results in the region (FR-MP-07). |
| ETH-03 | **Privacy of the pruned.** Suppressed blueprints show a neutral "no longer available in your area" state. The buyer's identity, purchase, and even the existence of the license are never revealed to other users. |
| ETH-04 | **No fake urgency artifacts.** No countdown timers, "3 people viewing this" widgets, or expiring-offer counts that do not correspond to a real mechanic. All urgency is real data or real deadlines (e.g., genuine price/introductory windows). |
| ETH-05 | **Cancellation & refunds.** One-click cancel for subscriptions; 14-day refunds on unlock, deploy, and license (with unprune on refund, FR-MP-09). Refund path is discoverable from the billing portal, not buried. |
| ETH-06 | **Opt-out of being counted.** Users can disable `consent_counted` (FR-SAT-09); their blueprint then never contributes to LocalDensity counts. Opt-out must not degrade their own product experience (a suppression flag, not a punishment). |
| ETH-07 | **Pressure guardrails.** The quiz and paywalls avoid known dark patterns: no pre-checked boxes, no opt-out-via-support, no forced waiting states to induce anxiety, no shame-based copy on decline ("this isn't for everyone" framing is banned in decline states). |
| ETH-08 | **Cold-outreach responsibility.** Outreach scripts are generated with a compliance header: reminder of CASL (Canada) / CAN-SPAM (US) consent requirements for email/SMS, and platform ToS compliance for DM outreach. The product ships a compliance checklist with every script (FR-BP-03). |
| ETH-09 | **Lead-gen tooling boundaries.** The premium scraping tool: rate-limited, scoped to public business listings, respects robots.txt/ToS of sources, and ships with a "responsible use" notice. Personal data minimization: only business contact data, only for the user's own outreach. |
| ETH-10 | **Marketplace integrity.** Workers vetted; escrow release only on acceptance or dispute resolution (FR-MK-05); platform never auto-releases to worker without buyer acceptance or mediation decision. |
| ETH-11 | **LLM content guardrails.** Blueprint generation prompt-injection resistance: user-supplied titles/skills are treated as data, never instructions; output schema validation; content policy filters on generated copy. |
| ETH-12 | **Children.** 18+ age gate at signup; no marketing to minors. |
| ETH-13 | **Legal review gate.** The saturation engine copy, density disclosures, and buy-out flow are reviewed by counsel before launch (FTC/US + Competition Bureau Canada framing: the numbers are true, so the claim "X operators near you" is factual). |
| ETH-14 | **Complaint monitoring.** The support funnel tracks complaints specifically about urgency/pressure mechanics (guardrail metric in §2.3); a sustained rate > 0.5% of activated users triggers a product review. |

## 12. Risks & Mitigations

| Risk | Severity | Mitigation |
|---|---|---|
| **API access loss** (YouTube/Instagram API changes, OAuth scope restrictions) | High | Upload fallback always available (FR-IG-05); adapter fixture tests + drift monitor (NFR-08); provider-agnostic event schema. |
| **"How did it know?" fails** → weak activation | High | Match rationale UI (FR-VM-05); post-render survey; iterate on skill-extraction prompts via versioned prompt experiments (NFR-09). |
| **LLM cost blowup under viral load** | High | Queue caps + per-user spend caps + provider TPM budgets (NFR-10); streaming render hides latency; DLQ + backoff (FR-AS-05). |
| **Scarcity mechanics read as manipulative** → PR/social risk | Med | ETH guardrails are launch blockers (ETH-01/04); disclosures (ETH-02); complaint monitoring (ETH-14); counsel review (ETH-13). |
| **License prune correctness bugs** (wrong region, double license, refund race) | High | Idempotent webhook handling (FR-MP-06), UNIQUE constraint on license, unprune on refund (FR-MP-09), integration tests over the full webhook→prune→generation path. |
| **Upload parsing edge cases** (huge files, weird formats, Google/TikTok schema drift) | Med | Streaming parser with memory caps (FR-IG-07), checkpoint resume (FR-IG-08), format fixtures in CI, per-file failure isolation. |
| **Casual users never reach ingestion** (quiz abandonment) | Med | Session persistence + remarketing (FR-QZ-03), resume UX, typed 0-event handling (FR-IG-05). |
| **Marketplace fraud / disputes (Phase 3)** | Med | Connect KYC, escrow release on acceptance, dispute flow (FR-MK-05), velocity rules (SEC-10). |
| **Regulatory drift (CASL/FTC/PIPEDA)** | Med | Counsel review gate (ETH-13), compliance checklist in scripts (ETH-08), consent-first remarketing (§10). |
